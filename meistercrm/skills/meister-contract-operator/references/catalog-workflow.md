# Connected MeisterCRM workflow

Discover the catalog search/list, item/contract read/write, file staging, validation, commit and attachment tools on the connected customer account. Read each tool's current input schema, accepted kind values, permissions and size limits. Before the first catalog change, check that each needed operation and its contract-workflow attribution are available in this connection. For workbook import, check staging, validation and commit individually. For PDF delivery also check the attachment tool. If a required operation or attribution is unavailable, finish the files, identify the pending action and reconcile before any later retry. Use the supported file import for the reviewed workbook. Scope the work to the authorized catalog and customer. Match owner master IDs using multiple identifying facts. For a room use the owning hotel. For a rate use its actual catalog owner. Read existing contracts across the relevant validity window, including pagination. Compare raw supplier currency without silent conversion; document an expressly authorized exchange rate and date. Align ages, pax, dates and local names across copies and verify eligibility after clipping to validity.

## Review on the master

Read the owning catalog master’s top-level `ai_source` and its current owner-visible values. Use `ai_source.ai_comment` only for a concise question whose answer is needed to proceed. Identify the affected rate, room or season and include the source page when it helps the customer answer. Keep the question within 400 characters. Track other open questions and source evidence on `Original` so they can be taken up in turn.

The customer can answer in `ai_source.ai_solution` or give a decision directly through MCP. Apply the answer only to the question it addresses and verify the affected work. If the reply is ambiguous or partial, ask precisely what remains unresolved.

Once the blocker is resolved, replace `ai_comment` with the next outstanding blocking question on that master. If none remain, explicitly send `{"ai_source":{"ai_comment":""}}` as the catalog update’s `fields`. Use the same rule when reviewing an old comment that only describes a settled decision. In either case send only the comment change within `ai_source` and preserve the customer’s `ai_solution`. Check the latest owner-visible values before writing in case the customer has replied again. Read the master back to verify the comment and the preserved answer. A retained reply to an earlier question applies only to that earlier question. If this question held a step in an authorized upload, resume that work as soon as the blocker clears.

Use hotel `notes` only for concise pricing adjustments or rules that a consultant must apply manually because the contract rows do not handle them. State the affected booking and what to do when quoting it. Record calculations and settled decisions, including a levy already incorporated into rates, on `Original`. See [short booking-exception notes](hotels/profile-upload.md#short-booking-exception-notes).

For changes made by this contract workflow opt in to server attribution on supported catalog item and single-contract mutations with `contract_workflow: true`. The server records the verified connected agent and UTC `last_update_timestamp` on the owning master; the nested `ai_source` string is the agent identity. Read the owner-visible list again to verify. Existing unchanged rows, duplicates and work performed outside this workflow require no stamp. Apply the reviewed basis to all eligible rows once. If a master is identifiable, create it and record the blocker even when every affected rate is held.

When an existing canonical location lacks an owned location detail, use `initialize_destination_detail` with `kind: "location"`, the resolved reference ID and `contract_workflow: true`. Read back the owned detail before attaching rates or review notes. For a requested gallery change in this workflow, pass `contract_workflow: true` to `attach_catalog_image` or to `attach_destination_image` for a location. Verify the returned asset and owning master. The source name comes from the stored authorized connection, with its client ID as fallback. Leave attribution opt-in unset for unrelated image work.

When an old contract appears superseded, preserve the record and its history. Update a uniquely identified single contract only when the requested correction and replacement terms are established. Otherwise ask on the master and hold the affected row. Do not delete old contracts to clear validation conflicts.

## Resume an upload after a blocker clears

An answer, updated source or changed preparation rule can make previously held work eligible. Treat an empty `ai_comment` as the end of the review question and resume the affected upload in the same workflow. Continue with independently eligible rows if another question still blocks a different room, period or product. Stay within the original authorized scope and any explicit limits the user set later.

1. Read the prior workbooks, source evidence, completion records and current catalog. Identify the exact rows or steps that were held. Start from their last verified checkpoint and reconcile partial writes against saved IDs before retrying. Reuse earlier work whose source, interpretation, inputs and target still match.
2. If the hold stopped preparation, rebuild the newly eligible rows in the same deliverable workbook and update `Original`. Reopen the final file and run the checking gates (see **Meister PDF to Contract**, Checking gates for contract delivery) for the affected data. Reconcile the new rows with existing coverage, and stage and validate the exact current workbook when the next step is an import.
3. Continue through the actual [import and attachment steps](#import-and-attachment). Obtain any required approval for the exact validated import and continue after it arrives. If rates were already saved, verify them and pick up the remaining checks and delivery steps. For hotels, complete all applicable [hotel completion gates](hotels/completion-gates.md), including saved-rate readback, available live buying-price comparisons, source attachment, tags and final delivery as scoped.
4. Report the upload complete only after every applicable gate is verified or has an authorized exception. If a permission, approval or other dependency prevents completion, report the last verified step and the exact remaining action. Keep the next unresolved contract question in `ai_comment` and record upload status in the working evidence.

## Import and attachment

1. Compare candidate contract identity (master/room, dates, currency, age/pax, occupancy, service/route and other pricing dimensions) and all commercial values with existing records. Use family-specific identity and importer rules. Skip exact matches. A changed payload with a uniquely identified existing contract is an individual correction through `update_catalog_contract` using the existing ID, changed commercial fields and `contract_workflow: true`. Re-read the contract. Stop ambiguous matches or conflicting overlaps for that row.
2. Stage the exact delivered XLSX, with **Contracts** first and **Original** second. Contracts contains the supported payable rows, including matches with existing contracts. Keep unpriced/ambiguous commercial terms only on Original. Validation filters duplicates and holds unrepresentable or conflicting rows while admitting distinct new rows. Review each reported outcome. Preserve both sheets in the submitted bytes even when only some rows are new. Current XLSX limits are 8 MiB for hotel, 5 MiB for flight and 2 MiB for other kinds. PDF files are limited to 5 MiB. Consult the connected tool schema for updated limits.
3. Call `stage_catalog_contract_file` with `filename` and binary bytes encoded once in `content_base64`. Pass its `file_id` to `validate_catalog_contract_import` with `kind` (`hotel`, `activity`, `addon`, `transfer`, `flight` or `location`), owning catalog `id` and `language`. The connected account needs its staged-file, validate, commit or attachment permissions for the relevant step. Review the actual proposed rows, existing conflicts, warnings and counts. Commit independently eligible new rows according to the validation receipt. For a later correction revise the same customer workbook and restage the corrected artifact for a fresh validation. Keep validation scoped to the file and target it covers. Once authorized, call `commit_catalog_contract_import` with that `validation_id` and `confirmed: true`. A ready receipt can be committed. Resolve a blocked receipt before import. For committed, partial or unknown outcomes, reconcile saved IDs and individual row results before retrying any missing rows. Read back amounts, dates and scope. Report pending validation or commit failures accurately.
4. Stage the exact lodge PDF and call `attach_catalog_contract_pdf` with `file_id`, owner `kind`, `id` and `confirmed: true`. Inspect current attachments and avoid reattaching unchanged documents. Verify the returned attachment or catalog file list.
5. Where a tool, write permission or supported file transfer is unavailable, finish the customer artifact and any independent work. Record the outstanding CRM step and missing capability in the handoff. Use the owning master’s review field only if the customer must answer a specific question for the work to proceed. Never request passwords or session tokens.

For a tax question, identify the source page, affected dates and components in the master comment. Apply the customer’s answer only to that scope. See Tanzania TDL decision examples (see **Meister PDF to Contract**, Tanzania hotel VAT and Tourism Development Levy).
